\title{Recovering Versioned Releases Across Build and Publish Boundaries}
\maketitle
\begin{abstract}
An npm engine feeds a Docker base; another image needs that published base
and an npm SDK. Premature builds and failures can lose work or change retry
versions. Git completion tags enable one-command recovery.
Package folders and shell stages span single-package repositories, monorepos
and polyrepos. Built-in readers cover 21 ecosystems and 36 manifest formats;
text replacement and configured commands integrate others without changing
provisioned CI workflows.
Environment checks (\code{if}) and loops (\code{for}) share Windows/Linux CI/CD logic.
Commits select releases, holds, prereleases and dependent-update scope.
Scoped empty commits request tests; last-commit windows retest repairs.
An agent skill guides commit diagnostics, planning and automation.
Docker supplies tools; a Terraform integration rebuilds temporary state
from known resources before dependent deployments.
Identical inputs yield identical plans, enabling caches.
Specified workers reuse release configuration across machines.
Our single-history model builds on saga, reconciliation and version-control
foundations: consumer work survives provider success; explicit retry assumptions
preserve versions and prevent repeated recorded releases.
Across 120 controlled failures, our protocol recovers all pending releases after repair;
discarding work after provider success loses releases in 70\% of those cases
(analytical comparison, not a tool benchmark).
Registry, CI, replay and scale experiments include google-cloud-node.
Historical fixtures handle mid-release commits, preserving conflicts for review.
Native Windows and distributed execution remain unevaluated.
Linux and LLVM results will be presented in the report.
\end{abstract}
