\title{Recovering Versioned Releases Across Build and Publish Boundaries}
\maketitle
\begin{abstract}
An npm engine feeds a Docker base; another image needs that published base
and an npm SDK. If the final image fails, its release must
remain pending after its providers succeed. We present a Git-based protocol
that tags completed releases and resumes unfinished work through the same
release command. Folders define packages and shell commands define stages
across languages, single-package repositories, monorepos and polyrepos.
Commits select releases, holds, prereleases, dependent updates and tests;
an agent skill supports diagnostics and automation. Shared Windows/Linux
configuration, containerized tools and extensible manifest readers let
provisioned CI reuse its workflow as packages are added. Terraform integration
reconstructs temporary state from known resources before dependent deployments.
Identical inputs produce identical, cacheable plans; the distributed profile
shares configuration and transports sources and results through Git.
Our evaluated single-history model builds on sagas and version control;
retry assumptions preserve versions and avoid repeating recorded releases.
All 120 controlled fault cases recovered after repair. Discarding consumer
work at provider completion would instead lose releases
in seven out of ten cases (analytical comparison, not a tool benchmark).
Registry, CI, replay and scale experiments include
google-cloud-node and selected mid-release commit conflicts.
Module suites include scanner/writer fixtures from real projects; release CI
requires the full suite regardless of change scope and checks binaries before
publication and installations afterwards. Native Windows and distributed
execution are outside these
measurements. Linux and LLVM results will be presented in the report.
\end{abstract}
