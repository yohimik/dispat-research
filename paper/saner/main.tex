\title{Recovering Versioned Releases Across Build and Publish Boundaries}
\maketitle
\begin{abstract}
An npm engine can feed a Docker base image, while another image needs that
published base and an npm SDK. Incorrect ordering starts builds too early;
incomplete recovery forgets unfinished packages or changes their versions.
We present a saga-inspired protocol using Git completion records to resume
unfinished work through the same release command.
Shared configuration supports Windows/Linux CI/CD across languages in
single-package repositories, monorepos and linked repositories (polyrepos).
Commits select releases, package holds and prereleases.
Commit scopes select tests even without file changes; a last-commit window
narrows retesting after repairs.
An agent skill guides commit diagnostics, plan review, tests and releases.
Planning is a deterministic, pure function: identical inputs permit cached results.
Specified extensions distribute tasks and releases across workers and repositories.
The model explains availability and preserves each consumer's pending work.
Eight guarantees hold under explicit retry assumptions, including stable versions
and idempotent recorded releases.
Exploratory outreach covers at least 211 repositories, without estimating defect prevalence.
All 120 controlled fault episodes recover after repair; an analytical alternative
discarding intent after provider success loses work in 84.
Registry, CI, replay and scale experiments include google-cloud-node.
Native Windows equivalence and distributed execution remain unevaluated;
external effects require safe repetition or reconciliation.
Linux and LLVM results will be presented in the report.
\end{abstract}
