| Topic | Required current statement |

| Admission | Direct and propagated work use the recipient's `Wfresh`; `W` is retained for aggregate train targets. |

| Determinism | Identical resolved inputs produce identical plans. Independent task completion order, lock identities and operational timestamps need not be identical. |

## Repository scope clarification

The conference title is now “Releasing Polyglot Projects as Distributed
Transactions,” and its abstract, introduction, Implementation section and
conclusion explicitly cover single-package repositories, monorepos and polyrepos.
The singleton workspace is a one-leg case of the same publish-then-tag protocol.
A single source project can model a CLI, container image and documentation as
separately recorded package legs. Multiple destinations inside one publish
script still share one package completion tag, so partial success inside that
script requires reconciliation.

The polyrepo construction uses a control repository with pinned git submodules
inside package wrappers. Pointer-update commits provide intent; history and
release tags in the control repository provide the formal model's single HEAD
and state. Linked histories remain separate. The construction does not add
a multi-history theorem or claim measured polyrepo operational scale. These
boundaries were checked against the single-package and control-repository docs
and independently against the executor. English remains 9 pages including
29 references, with 41 unique resolved labels and no overfull boxes.
