Recoverable Releases Across Package Registries:
A Git-Backed Saga Protocol
Abstract—Releasing interdependent packages writes irreversibly to independent registries without a coordinator or
rollback. A partial failure can therefore leave a consumer
permanently behind a dependency that was published.
This paper presents CCME, a commit-message language and
release protocol for resumable releases, and dispat, its opensource implementation for single-package repositories, monorepos, and polyrepos joined through a control repository. In the
formal model, release state consists of git tags, the plan is
a pure function of repository history, dependency graph and
conﬁguration, and propagated work is admitted against the consumer’s pending window. We prove eight guarantees, including
no orphans, exactly-once ledger discharge and convergence under
an explicit retry invariant. Minimal counterexamples establish
why delivery must be tracked per consumer, why prerelease
aggregation needs a separate window, and why retry guarantees
require stable channel and suppression predicates.
Against the ofﬁcial dispat 1.8.2 image, the fresh campaign
passes six selected CCME 2.0 regressions, agrees with a restricted
reference oracle on all 1,500 core instances, recovers 24/24
injected-failure episodes within four runs, and completes eight
scale cells. The full proﬁle intentionally generates regressive
prereleases: 997 plans were accepted and 503 complete diagnostic
plans were rejected with E195. All 1,914 differing rows retain
their heuristic classiﬁcation and stated coverage limits.
Index Terms—release engineering, semantic versioning, sagas,
partial failure, idempotency, deterministic replay

I. I NTRODUCTION
A release workspace can contain one package, several
packages in a monorepo, or packages drawn from separately maintained repositories (a polyrepo). Releasing it means
choosing versions for the packages that need them, writing
those versions into manifests, building artefacts, uploading
them to registries, and recording what happened. In a modern
project the registries are plural and heterogeneous: an npm
package sits next to a Go module, a Docker image, and a
documentation site, all wired into one dependency graph.
The recording is the hard part. Independent registries offer
no atomic transaction spanning the release: each publish leg
may succeed or fail, and the outcome may be lost before
the corresponding git tag is written. This is a long-running
transaction over separately committed resources, the setting
for sagas [1]; recovery must complete or reconcile successful
legs rather than assume a cross-registry rollback.
Existing tools expose different ledgers and recovery boundaries. Lerna, Nx [18], release-please, and Changesets [16]
automate releases, while semantic-release [17] targets one
package per repository. Their pinned fault experiments below
show that registry queries, intent ﬁles, and tag timing answer

different parts of what an interrupted cross-registry run still
owes.
This paper treats the release as the transaction it is, and
makes three contributions:
a commit-message language, CCME, in which release intent (blast radius on two separate, one-way-coupled axes,
version bumps and prerelease channels) is reviewable text
in the commit (Section III);
• a formal model of the release computation and publish
protocol, self-contained in this paper, with eight guarantees proved over it (Sections IV and V); minimal
counterexamples identify necessary design choices and
the explicit invariant under which retries preserve the
guarantees (Section VIII-C);
• dispat, an ecosystem-agnostic implementation in which a
package is a directory and a stage is a shell command,
evaluated by differential validation, selected CCME 2.0
vectors, recovery campaigns, replay, and pinned fault
experiments (Sections VII and VIII).

II. M OTIVATING E XAMPLE
A workspace holds a library core and three consumers
cli, ui, api, each depending on core. A commit C lands
with the message feat(core)ˆ: streaming reader:
core takes a minor bump, and the caret propagates a patch
bump one edge outward. The run publishes core@1.5.0,
ui@0.9.2 and api@1.2.1, tagging each on success, and
then cli’s publish fails, for any of the reasons registry writes
fail.
The natural expectation is that re-running ﬁnishes the job.
Whether it does depends on one deﬁnition. Suppose the engine
keeps a commit’s release intent alive only while the commit’s
own package still has it pending, the natural reading. Then on
the second run core has released C, so the unit has no source
packages, propagates to nothing, and cli is never released,
on this or any future run. cli is orphaned: permanently one
patch behind a dependency it declares, with no diagnostic,
because from the engine’s point of view nothing is pending.
The failure is silent, and grows more likely with the fan-out.
The repair is a one-line change of deﬁnition: a unit propagates to a dependent exactly while the dependent’s pending
window still contains the unit’s commit (Deﬁnition 10). Catchup then needs no repair pass or side state when prior outcomes
are conﬁrmed by tags; an uncertain external publish/tag gap
still requires identity reconciliation. Section V proves the
guarantee this buys (G2, no orphans) and its siblings.

III. CCME: T HE L ANGUAGE
CCME is a strict superset of Conventional Commits 1.0.0 [7] over a stated conforming subset. One commit
message is a sequence of units separated by a whole-line separator (--), each an independent conventional-commit-shaped
block with its own header, body and footers, so a squashmerged pull request describes several unrelated changes without one lie of a type for all of them:
feat(@acme/core)^^minor%beta++*: reader
--fix(@acme/cli): correct exit code on SIGINT
--cancel(@acme/legacy-adapter): reset state

Scopes name packages, or are derived. The scope is
a comma-separated package set, globs with exclusions
(feat(*,-docs)), or absent, in which case the affected
set is derived from the ﬁles the commit changed, package
by owning directory. Derivation makes ordinary unscoped
commits release the packages they touched.
Two axes, two depths. A commit answers two separate
questions about its dependents: how far does the version bump
travel, and how far does the prerelease channel travel. Both
default to depth zero: a commit that says nothing releases its
own packages and nothing else. The bump axis is written ˆ
(direct consumers), ˆˆ (transitive closure) or +N; the channel
axis % (own packages change channel), %% (dependents do),
++N (how far). Every sigil desugars to a footer; the header
above desugars to
feat(@acme/core): reader
Propagate: minor
Channel: beta
Propagate-Depth: all
Propagate-Channel-Depth: all

reading: core takes a minor bump and enters the
beta line, every transitive dependent takes a minor
bump and follows it onto beta. Channel values may
be transitions <from»<to>: move only packages currently on <from>. Transitions make graduation idempotent: release(@acme/*)%beta>stable: ship graduates whatever is still on beta and can be replayed safely after
a partial failure.
Cancellation and corrections. The type cancel discards
a scope’s accumulated unreleased release metadata; a unit
is cancelled for a package when its commit is an ancestoror-self of the cancelling commit; ancestry, unlike timestamps, is deterministic under merges and rebases. The footers
Edits: <sha> and Deletes: <sha> restate or discard
a named past record: a commit fix(core): rewrite
internals carrying Edits: <sha of A> replaces A’s
pending major with this unit’s patch, so core releases
1.4.3 rather than 2.0.0. Corrections reach only unreleased work and only strict ancestors; the newest correction
wins; a correction whose own record is discarded is void.
Release-As: none holds a package until lifted; an exact
Release-As pins one version.

IV. T HE M ODEL
This section deﬁnes the release computation and the publish
protocol; Section V proves the guarantees over these deﬁnitions and nothing else.
A. Workspace, State, Windows
Deﬁnition 1 (history). The history is a ﬁnite DAG of commits
with a distinguished HEAD = h; reach(c) is the set of
commits reachable from c by parent edges, including c; write
c′ ⪯ c for c′ ∈ reach(c). h is ﬁxed throughout. This reading
of a repository is the standard one: the commit DAG with
reachability is the working model of git history in repository
mining [9], and the same structure underlies formal derivations
of git’s three-way merge from least common ancestors [10].
Unlike the patch-theoretic accounts of version control [11],
[12], [13], this model tracks no ﬁle contents at all, only history,
tags and messages, which is what makes the plan a pure
function of the repository.
Deﬁnition 2 (workspace). P is the ﬁnite set of packages at h;
E ⊆ P ×P contains (a, b) when a declares a dependency on b
of a conﬁgured kind; dep(p) = {d : (d, p) ∈ E}. The graph is
acyclic (a cycle is a repository-scoped error: no publish order
exists for it, so whichever member went ﬁrst would declare a
range on a version that does not exist). For S ⊆ P, δ(S, d) is
the least number of edges on a chain from a member of S to
d against the arrows, ∞ if none.
Deﬁnition 3 (bumps, versions, channels). B = {none <
patch < minor < major} is a chain, hence a join-semilattice
under ⊔ = max. Versions are SemVer 2.0.0 [6] with its precedence; ch(v) is stable for a non-prerelease v and otherwise v’s
ﬁrst prerelease identiﬁer; core(v) and cnt(v) are the numeric
triple and the prerelease counter; apply(v, b) applies a bump.
Deﬁnition 4 (state). A state σ is a ﬁnite set of release tags
(p, v, c) with c ⪯ h; states are ordered by inclusion. base σ (p)
is the highest-precedence version among p’s tags, sbase σ (p)
the highest-precedence non-prerelease one, basec σ (p) and
scom σ (p) their commits; ch(base σ (p)) = stable by convention when p has no tag. Tags are never moved or deleted,
so states only grow: a tag is the record that a leg of the
transaction completed, and a rewritten record is what makes
a saga unrecoverable. Tag write access is therefore release
authority; a manifest’s version ﬁeld is not the release ledger.
Manifests, conﬁguration, and derived scopes remain trusted
planning inputs.

A graph walk may be cached safely when source set, depth
and edge kinds match; merging by window and directive
spelling is unsafe because admission, cancellation, scope,
self-source exclusion, inherited channel and provenance remain per unit. Lexical parsing may be cached by repository,
immutable record, parser/schema and parsing-conﬁguration

separately. Channel incidence inversion costs O(U + I + |P|).
These are informative implementation costs, not required endto-end bounds; semantic equivalence and deterministic output,
including provenance, remain normative.
Order matters for a reason tags cannot express: a dependent
published before its dependency carries a range reconciled
against the old version, both land at the same commit, and
no later run can detect the inversion from ancestry, so it is
prevented, not diagnosed. When a publish is rejected because
the version already exists (a run died between publish and
tag), CCME 2.0 requires content-identity veriﬁcation before
adoption and otherwise aborts: tagging a foreign artefact
would enrol it into the release lineage. This is a protocol
obligation, not a claim that dispat can inspect arbitrary userdeﬁned publish scripts; such integrations must supply an
idempotency or identity check.
Theorem 1 (determinism). Π(σ), νσ , the publish order and
the diagnostics are functions of (σ, h, conﬁg) alone.
Proof. Every deﬁnition above is a closed expression in those

D. Instantiation: What the Theorems Say About a Repository
The deﬁnitions above are parametric, and a theorem about
the model is worth nothing to an operator unless it is a theorem
about their repository. A concrete repository at a commit
determines one instance
I = (commits and parent edges, h, P, E, U , σ, conﬁg) :
the commit DAG and HEAD are read from the repository, the
packages and edges from its manifests and conﬁguration, the
units from its commit messages, and σ from its tags. Every
quantity the model deﬁnes is a computable function of I: the
sets are ﬁnite, ancestry is decidable, and no deﬁnition consults
anything outside I. The model is a fragment of repository

behaviour: it abstracts artefact contents, hook semantics, and
conﬁguration features not represented in I. The theorems of
Section V are universally quantiﬁed over instances of that
fragment, subject to acyclicity, the version guard of Deﬁnition 11, and the retry invariant stated below. The latter is a
property of the run sequence, checked again before each retry,
rather than a static property of one instance. What remains
between the theorems and a running binary is a reﬁnement
claim, that the implementation computes this model’s Π(σ)
and νσ and executes Deﬁnition 12’s protocol. That claim is
not proved here; it is tested, by Section VIII-B’s vectors (each
ﬁxes a small instance and the plan the model assigns it) and
by Section VIII-A on randomised instances.
V. G UARANTEES , WITH P ROOFS
Cross-run claims use the retry invariant: the corrected
tuple stream, source sets, graph, scope/depth predicates, target
baselines, and resolved source/target channel admission of
every outstanding unit remain unchanged, except for baseline
tags written for successful packages. Two recurring components deserve names. (H1) says every baseline channel read
by Propagate-Channel: inherit remains unchanged;
(H2) says no contribution initially suppressed by cancellation,
hold, or correction is later released at the same h. H1 and
H2 are necessary in their respective cases but are not, by
themselves, the full retry invariant. Neither is needed for one
invocation’s determinism.
Lemma 1 (window antitonicity). For σ ′ = run(σ, F ),
Wσ◦′ (p) = ∅ if p published and Wσ◦′ (p) = Wσ◦ (p) otherwise.
The train window W also empties after a stable release, but
may remain unchanged after a prerelease release.
Proof. The run adds only tags at h. If p gained none, both
baseline commits are unchanged. If it published, basec σ′ (p) =
h, so Eq. 2 subtracts reach(h) and is empty. Only a stable
release also makes scom σ′ (p) = h.
Lemma 2 (source stability). Under the retry invariant,
src σj (u) is constant for every outstanding unit throughout a
valid run sequence.
Proof. The corrected tuple stream and its cancellation, hold,
correction, and source-set predicates are ﬁxed components of
the invariant. H2 is the component excluding later release of
an initially suppressed contribution. Arbitrary tag-set inclusion
outside a valid run sequence implies no such monotonicity,
because a higher-version tag may point to an earlier commit.
Lemma 3 (retry stability). Under the retry invariant, an unreleased package’s resolved channel, each outstanding unit’s
source-channel set, and rsv (u, d) remain constant.
Proof. These are precisely the channel and source-set components ﬁxed by the retry invariant. Deﬁnition 9 then selects the
same direct or propagated proposal, and Eq. 4 reads the same
sets.

bump pass then reads its resolved channels through Eq. 4.
Proposition 1 (universal tagging is necessary). If a released
package with no artefact to upload and a non-empty effective
bump were versioned but not tagged, its window would never
advance (Lemma 1), it would re-enter every plan forever, and
G6 would fail. Hence Deﬁnition 12 tags whatever is released,
and the convergence check (re-plan after a fully successful run;
a non-empty result is an error) admits exactly one exclusion,
held packages.
Three corollaries carry the operational weight. Resumption:
after a partial failure, Π(σ2 ) = F ∪ B at the versions of run 1
(G2–G5), so the next run does the rest of the same job with
no ﬂags and no cleanup. Idempotency: running twice with no
intervening commits, tag changes, or conﬁguration changes
gives the same plan (Theorem 1); running after full success
gives the empty plan (G4). Review soundness: while the retry
invariant holds, by G5 the plan a reviewer approves before
the ﬁrst attempt is an upper bound on everything every retry
can publish, so an attacker who can induce a publish failure
cannot enlarge what a commit releases, and no resume needs
re-approval.

In the pinned conﬁgurations we executed, Lerna and nx

failed upload is absent from their tag ledger; release-please

tags after publish, consumes intent ﬁles, and queries npm

leg and therefore retains debt in git, subject to the external

VII. I MPLEMENTATION
dispat is a statically linked Go binary whose releaseplanning state is only conﬁguration, history, and tags. Packages
are folders and lifecycle stages are shell commands; scanners
and byte-preserving writers cover 35 manifest formats in
twenty ecosystems. The planner implements the deﬁnitions
above; topological execution continues independent subtrees
after a failure and skips consumers of failed packages. A
remote reserved tag serialises release runs. Successful external effects are not rolled back: later tag, record, or push
failure leaves reconciliation work under the publish-thenrecord protocol. Invoked tools, including Terraform, retain
responsibility for their operational state and identity checks.
The implementation is tested through vectors, black-box CLI
runs, fuzzing, real manifests, and the campaigns below.
a) Repository layouts and saga granularity.: For a
single-package repository, P = {p} and E = ∅: propagation
is vacuous, but version planning, publish-then-tag recording
and recovery still apply. This is the one-leg case of the
saga protocol. Dispat requires the package in a subfolder; the
conﬁguration and release ledger remain at the root. Multiple
destinations inside one publish script still share one completion tag, so partial external success requires reconciliation;
separate package legs provide separate completion records.
A single source project can expose its CLI, container image
and documentation as such legs. For a polyrepo, a control
repository pins linked repositories as git submodules inside
package wrapper folders. Its pointer-update commits express
release intent; its history and tags provide the model’s single h
and σ. The linked repositories retain their own histories. This
supplies one release graph without merging the source repositories, rather than a distributed transaction over independent
git histories. This construction establishes applicability; the
evaluation does not measure polyrepo operational scale.

a Linux CI runner can share global.yaml (graph,

C. Defect-Finding Power of the Formalisation
Minimal counterexamples identify why several apparently
simpler designs fail. They serve as regression obligations and
explain the model’s assumptions.
1) Aggregation is not discharge. Reusing a stable-baseline
train window for fresh admission can produce beta.1,
beta.2, . . . without new commits. Separate W and W ◦
retain train intent while discharging delivered work.
2) Suppression must remain stable across retries. If a
cancelled or corrected source is later released, its discharged record can change the source set and reach new
consumers. H2 excludes this widening within a reviewed
retry sequence; changing it requires a new plan.
3) Inherited channels are mutable inputs. The graduation
example in Remark 1 changes a failed consumer’s next
version unless H1 preserves its inherited-channel inputs.
4) Reverse audits need the full admission predicate. A
consumer-side staleness audit that omits channel eligibility or target self-exclusion can disagree with forward
propagation.
5) Axis independence is one-way. Resolving channels can
make a dependency ineligible and suppress a bump;
suppressing a bump does not suppress a channel change.
Resolving channels ﬁrst preserves this order.
6) Shared graph traversal does not merge unit identity.
Subtracting a union of source sets excludes legitimate
targets of other units; admitting every traversed node can
include a unit’s own source. Traversal may be shared,
but admission and provenance remain per unit.
These counterexamples motivated the released rules used in
the model. Their role here is to establish design necessities,
not to claim defects in the current speciﬁcation. The selected
released-binary vectors cover six cases; they do not establish
full implementation reﬁnement.
IX. T HREATS TO VALIDITY
Internal. The vectors, the tests and the formal model were
produced by the same author as the system, so they share assumptions and their agreement cannot catch an error common
to all three. The guarantees are proved of the model, not of
the Go code; the link is the vector suite, the tests and the
differential run of Section VIII-A, which covers the planner
but not the run’s protocol. The concurrent-push experiment
is the strongest evidence for that protocol, and it is one
deterministic interleaving per tool, not a sweep over every
point a push could land. External. The self-hosting study is one
repository of moderate size administered by the tool’s author;
it demonstrates feasibility and recovery on real history, not
usability at organisational scale. Ecosystem generality is by
construction plus tested writers and manifest ﬁxtures, chosen
by us rather than a ﬁeld study. Construct. Conformance is
measured against a contract the implementation co-evolved
with; Section VIII-C shows this cuts both ways. No user
study supports reviewability claims; we claim only that the
blast radius is written in the message, not that authors write it

correctly. The characterisation of release-please is read from
its documentation; Lerna, nx and Changesets are executed on
two faults in the pinned six-package ﬁxture summarised in
Section VI. The check counts recorded for those tools describe
what each leaves behind against the questions dispat’s protocol
answers, not a score on a shared scale. The experiments
run in containers on one machine and one CI provider; the
replay conﬁgurations for the subject repositories were reverseengineered from their layouts and may misread conventions
their tools resolve differently.
X. R ELATED W ORK
Adams and McIntosh survey release engineering as a ﬁrstclass subject [20]; Potvin and Levenberg document Google’s
monorepo practice [21], whose build layer solves ordering
and caching but not versioned publication to external registries. Among release tools, semantic-release [17] established commit-driven versioning; Lerna [15], changesets [16],
Nx [18] and release-please [19] extend automation to monorepos within, predominantly, one ecosystem each; Section VI
states their computations as instances of this paper’s model
and locates the structural difference in the tag discipline.
Empirical studies show declared version semantics and actual compatibility diverge [22], [23]; Decan et al. study
dependency-network evolution across ecosystems [24]. Together they motivate explicit release intent over a dependency
graph. Formal treatments of version control (semantics of VCS
operations [11], patch theories as higher inductive types [12],
merges as pushouts [13]) model contents and merging; this
paper’s model keeps only the DAG, tags and messages, the objects repository mining treats as git’s model [9] and mergeabletype derivations build on [10]. Packages and dependency
graphs as formal objects go back to the EDOS work on
distribution consistency [14]. Within the literature surveyed
here, we found no earlier composition of these objects into
this release protocol. The protocol adapts sagas [1] to legs
for which no acceptable compensating action is available; we
therefore choose forward recovery in light of transaction limits
described by Gray [2]. Helland’s arguments for independently
committed, idempotently reprocessable steps [3], [4] describe
the discipline G2–G6 impose. Kahn’s algorithm [5] underlies
the publish order; Mokhov et al.’s build-system taxonomy [25]
clariﬁes what dispat is not: it has no incremental rebuild layer,
because unchanged packages are absent from the plan rather
than cached. Fuzzing is reported under the cautions of Klees et
al. [26]. The nearest formal-guarantees work in operations is
Anvil [27], which veriﬁes that Kubernetes controllers reconcile
to a desired state; convergence here instead comes from a
ledger, replay, and explicit reconciliation of uncertain external
outcomes.
XI. C ONCLUSION
Across single-package repositories, monorepos and controlrepository polyrepos, CCME treats release publication as a
saga. It records intent in commit messages, completed publication legs in tags, and admits propagated work against

each consumer’s own fresh-work window. Under the retry
invariant, its eight guarantees make deterministic replay a
correct recovery procedure. Minimal counterexamples show
why separate admission windows, stable retry predicates,
and per-unit provenance are necessary. The pinned releasetool fault experiments support the operational distinction in
the pinned conﬁgurations: dispat resumes a refused upload
and preserves tag reachability across a concurrent push; the
compared runs required external recovery.
Remaining work is to mechanise the model and proofs in
Lean or TLA+ [28] and extend differential validation from
plans to complete runs, including randomised interleavings of
tagging and merging.
