## Features and why they matter

### Already present in the 1.9.0 paper: validated commit authoring

`dispat commit -m "feat(core): add streaming"` validates the final commit message using the existing CCME parser before Git creates the commit. It preserves existing hooks and validates after hook/message-cleanup processing. Authoring flags select this mode; bare `dispat commit` already had a distinct release-commit role.

Git may reject a commit with no staged changes before reaching the validation hook. The user explicitly said **not to fix** this behavior. Do not reopen that old issue. The new standalone diagnostics command addresses checking text without requiring a staged commit.

### New in 1.10.0: standalone diagnostics

Examples:

```sh
dispat diagnostics 'feat(core): add streaming'
dispat diagnostics --config dispat.yaml --log-format json 'fix(api): close stream'
dispat diagnostics -- '--not-a-commit'
```

- Accepts one literal string, including empty or multiline input. It does not perform Git message cleanup.
- Without `--config`, uses parser defaults, ignores nearby project configurations, and requires no Git repository.
- With explicit configuration, loads the normal full dispat configuration schema and references relative to `--root`; missing or malformed configuration fails without fallback.
- Exit codes: 0 for valid input or warnings, 1 for diagnostic/configuration errors, 2 for usage errors.
- Pretty or JSON diagnostics go to stdout. Usage/configuration errors go to stderr.
- Warnings remain visible under quiet/error-only logging; debug and trace behavior is preserved.
- No Git operation, manifest scan, script execution, release planning, or update check occurs.
- It does not establish that a scope exists, a release plan is correct, or an action is authorized. Use `status` for the plan.
- A custom script named `diagnostics` now needs explicit `dispat run diagnostics`.

Purpose: editors, agents, and commit generators can validate text without duplicating the CCME grammar or staging files and creating temporary commits. This is a useful authoring/CI integration, not a new release theorem or scheduler algorithm. The parser and release protocol did not change.

Relevant public-repository files include `services/dispat/internal/app/commit_validation.go`, CLI dispatch/usage/diagnostics tests, and `tests/integration/diagnostics_test.go`. Read implementation and docs before proposing experimental claims.

### Agent guide

`specs/agent-guide/README.md` now instructs tooling to use `dispat diagnostics` and agents creating commits to use `dispat commit`. Releases should follow configured CI/CD paths rather than manual publication. Tool-heavy pipelines can use DinD where a dedicated daemon is supported, or an appropriate existing daemon/BuildKit service. Cache configuration must be explicit and scoped; validate cold and warm paths and keep secrets out of images. Build caches are not persistent release-state stores.

## Mathematical boundaries to preserve

The existing eight guarantees are conditional properties of the model, not eight mechanically verified implementation properties:

1. Propagation termination, with the stated O(units × (packages + edges)) bound.
2. No orphan obligations.
3. Version stability.
4. No double ledger delivery/discharge, with eventual-success assumptions where relevant.
5. No widening.
6. Convergence when each nonempty retry makes progress.
7. Channel discharge.
8. One-way axis independence.

Preserve the fixed normalized inputs/admission assumptions, retry invariant, history ordering, train versus fresh-window distinction, cancellation/guards/channels, and the distinction between consumer→provider package edges and provider→consumer stage order. Keep the model-to-implementation refinement gap explicit.

Keep `release(s) = release(release(s))` for successful recorded releases under the stated assumptions, with an adjacent disclaimer for external publication that succeeds before its tag/record is written. Reconciliation or an idempotent publisher is needed for that ambiguous interval. Ledger idempotence does not imply exactly-once external side effects. Permanent failure or retries without progress have no finite convergence bound.

“No additional persistent release-state store” refers to the Git release ledger; registries, build caches, and Terraform state can still exist. Do not turn this into “no cache/database/state anywhere.”
