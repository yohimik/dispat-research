# Kernel build parity experiment, 2026-09-22

The tested candidates do not yet meet the 1x reference-time gate. This is a
targeted image-build experiment on three architecture groups, not evidence for
the complete 57-group image/QEMU matrix.

## Acceptance boundary and reference

The candidate gate is GNU `time` elapsed from invoking `dispat release` until
it exits. It includes source snapshot transport performed by the release,
assignment and claim polling, worker checkout, the complete build script,
result transport and coordinator reporting. VM provisioning, toolchain setup,
one-time source preparation and `dispat compute` are outside that interval.
This benchmark did not invoke `dispat compute`; that command prepares manifest,
dependency and link configuration rather than executing the release.
The tested development binary's SHA-256 was
`a7172a7feb21e27ce882050120b9e04df1e6d4b4ee5f3341ab8a99ba155ba70a`;
these are observations of that distributed-release build, not a benchmark of
the current `../dispat` working tree. That working tree was inspected read-only
and was not modified.

[`parity-20260922-reference.json`](parity-20260922-reference.json) retains the
public references. Every accepted case must have the same revision, compiler,
assembler (where reported), exact case lines, and an elapsed time no greater
than the reference:

| Group | Reference | Toolchain | Exact cases | Source |
|---|---:|---|---|---|
| alpha | 623 s | `alpha-linux-gcc (GCC) 16.2.0`; GNU assembler 2.47.20260726 | `defconfig`, `allmodconfig`, `allnoconfig`, `tinyconfig` | [build 332](https://kerneltests.org/builders/upstream-alpha-master/builds/332) |
| hexagon | 111 s | Ubuntu clang 18.1.3 (1ubuntu1) | `defconfig`, `allnoconfig`, `tinyconfig` | [build 330](https://kerneltests.org/builders/upstream-hexagon-master/builds/330) |

## Results

The scripts run on these machines:

| Machine | Resources | Role and scripts |
|---|---|---|
| `parity-orch` | e2-standard-2 | The phase runner invokes `dispat release`; this machine holds the Git source/task refs and collects completion records. It does not compile kernels. |
| `parity-c3` (`w1`) | c3-standard-22: 11 physical cores, 22 hardware threads | `worker.sh` starts one worker slot. Each assignment invokes `run-cell.sh`, then `stable-build-arch.sh` with its architecture and optional configuration subset. |
| `parity-t2d` (`w2`) | t2d-standard-8: 8 physical cores, 8 hardware threads | The same worker/wrapper/build chain, with one worker slot. |

The control's observed order was hexagon → m68k_nommu → alpha, all on `w1`.
Those architecture packages have no ordering dependency on each other. In the
candidate runs, a ready package goes to an available worker. Inside each
package, the farm script executes the selected configurations sequentially in
the original architecture array's order. Each node has its own bare kernel
cache; each package gets an isolated kernel worktree and build-output directory.

The workers were heterogeneous: `w1` was the 22-vCPU C3 machine and `w2` was
the T2D8 machine. `script` below is the complete build-script body, including
configuration, compilation, linking and script cleanup; it is not compiler CPU
time and is not compared directly with the full reference duration.

| Candidate | Placement and script seconds | Release | Reference | Gate |
|---|---|---:|---:|---|
| split hexagon | `w1`: defconfig 69; `w2`: tinyconfig 54, allnoconfig 76 | 170.07 s | 111 s | fail: elapsed only |
| split m68k_nommu | `w1`: m5272 35, m5407 34, m5249 35; `w2`: m5307 65, m5475 49 | 159.03 s | 128 s | fail: elapsed only |
| batched hexagon | `w1`: allnoconfig+tinyconfig 65; `w2`: defconfig 147 | 165.30 s | 111 s | fail: elapsed only |
| batched m68k_nommu | `w1`: first two cases 66; `w2`: last three cases 167 | 196.23 s | 128 s | fail: elapsed only |

For every completed candidate, `compare.py` accepted the exact cases,
toolchain identities and revision and rejected only elapsed time. The outer
experiment epochs were 170.189 s, 159.155 s, 165.475 s and 196.452 s
respectively; they also include the small wrapper work before and after
`dispat release` and are retained in the raw summaries.

The cold, grouped control ran all three groups sequentially on `w1`. Its
release took 1797.75 s, while the three build-script bodies totalled 1608 s
(hexagon 130, m68k_nommu 154, alpha 1324). Per-group assignment-to-result
intervals were 229, 173 and 1340 s. Those are lower bounds inside one
multi-group release, not standalone phase measurements; each nevertheless
already exceeds its matching reference.

The first control release transported the full 1.4 GB Git repository / 1.9 GB
working tree. Its initial source phase took 45 s, of which the recorded Git push
was 44.392 s. The image-only harness excluded unused QEMU assets and reduced
transport to about 512 KB. With source and coordination refs consolidated in
one repository, later candidate source pushes recorded only 0.031-0.050 s.

Each worker kept one bare kernel cache and created a separate worktree for each
cell. In the warm-source candidates, kernel fetches took 0.446-0.571 s and
kernel checkouts 7.026-8.327 s per cell. Assignment-to-claim polling took 1-4 s,
and worker completion-to-coordinator receipt took 1-5 s. A worker received its
next assignment in the same timestamp second as the preceding coordinator
receipt, so measured scheduler queue gaps were 0 s; the 3-5 s delays seen in
some paths were claim/result transport polling, not idle scheduler gaps.

Splitting exposes configurations to both workers, but loses build-directory
reuse and adds a checkout and dispatch for each cell. Batching preserves reuse
inside a group. The batched hexagon trial illustrates the heterogeneous tail:
the two-case C3 task finished much earlier than defconfig on T2D8, leaving the
release gated by the slower worker. Batched m68k showed the same effect: the
C3 first-two task took 66 script seconds while the T2D8 last-three task took
167, making its 196.23 s release slower than the split candidate. Neither
scheme has met parity in a single trial, so these measurements do not establish
a repeatable improvement.

About 89% of the control's release elapsed time was inside the build scripts.
During the long alpha compilation, CPU samples showed approximately 90–91%
user time and 9–10% system time, with no material idle time or I/O wait.
Alpha's script alone took 1324 s against a 623 s reference. Removing all of its
dispatch and Git overhead would therefore still leave this candidate too slow.

## Implementation and limits

The experiment added an image-only source export, exact configuration
selection, configurable build jobs, independent result directories, checkout
timing, and a reusable timeline analyzer. Source and task refs may share the
coordination repository. Configuration-level packages can be split or
explicitly batched while retaining the farm script's original order within a
batch.

The kernel source cache was warm for candidate phases, but compiled outputs
were fresh. The control began with different cold-source conditions. The C3
and T2D8 machines also differ from the public reference farm, so these trials
test parity of observable results and elapsed time rather than identical
hardware performance. There was one measured trial per candidate.

Optional distcc support was prepared but remains **unmeasured**. It must not be
credited with any result above. Additional capacity was proposed but not
provisioned; further cloud runs are deferred. Failed setup attempts, including
`batched-hexagon-setup-failure`, are
kept separately and are excluded from timed candidates. All three benchmark
VMs in `dispat-linux-parity` and their attached disks were deleted at the user's
request after evidence collection. Subsequent listings confirmed no instances
or persistent disks remain in that project. The original `dispat` project was
not changed.
