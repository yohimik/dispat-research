## 3. Protocol: `publish` assignments with the ready/go handshake (`execution/coordinator.go`, `execution/worker.go`, state machine from gate 6)
- `Coordinator.Publish`: snapshot (same per-dispatch rules; by publish time the working tree also holds later packages' version edits: that is fine, the input check above is what guards relevance) → `Pool.Acquire` (platform filter = the package's `buildPlatforms`; prefer the node that built the package when it has a free slot, because its cache already holds the objects: a preference, not a requirement) → assign `publish` with `frame {before, commands}` (no login, ever; no `after`: `postPublish` is orchestrator-side), `permits {publish: true, nativeRefs: false}`, `inputs[]` = the package's OWN admitted output set (kind `outputs`, path = its own dir) plus the same provider inputs its build received, computed env for stages `beforePublish` and `publish`, unresolved static env, shell.
- Worker: claim C → checkout + install inputs (gate 9) → `beforePublish` hook → push H `ready` (json: header + `hookExports`) → wait for the tip to become G or X, polling the single branch with the same back-off, bounded by `timeouts.task` → on G: verify signature, header echo, that G's first parent is exactly this worker's H, THEN immediately before starting the publish command re-read the REMOTE tip once (one `ls-remote`): it must still be G (the fence at the effect site: an X pushed after G but before the command started stops it) → run commands → R with exports. On X before G: never start the command; push K; R is not needed. On timeout waiting for G: push R `failed`/`authorization` and release the slot.
- G carries `notAfter` (issue time + 120 s) and the assignment carries `deadlineSeconds`; the worker refuses to start the publish command after `notAfter` and enforces the deadline itself (gate 12 completes the deadline handling for every task kind; in this gate implement it for publish and leave one shared function for gate 12 to reuse).
- Orchestrator on H: validate (signature, header echo, chain A→C→H) → run `authorize(ctx)` → success: push G (CAS on H; single use: the Coordinator marks the attempt authorized BEFORE pushing, and an attempt is never authorized twice; a CAS loss re-reads: if the tip is already its own G, continue; anything else fails the task) and log info `publication authorized` (package, node, run, task, attempt); failure: push X, await K briefly (`timeouts.cancel`), fail the package with the authorize error (validation label). Then wait for R. The detailed timeout / lost-worker / outcome-unknown handling after G is GATE 12: in this gate a missing R after G within `timeouts.task` fails the package with E228 `publication-unknown`, marks the node unhealthy and leaks its slot, and the run exits non-zero; do not release-then-retry anything.
