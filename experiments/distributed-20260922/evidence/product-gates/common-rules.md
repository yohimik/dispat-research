Hard rules
- NEVER push, never create release tags, never run `dispat release` or bare `dispat` in this repository. Commits only, on this branch.
- Never create plan/review/summary/notes markdown files in the repository. Findings go in your final message.
- Only feature-related changes. With `execution` absent (or `workers` empty) behaviour must stay byte-for-byte identical and EVERY existing test must pass UNMODIFIED. Do not edit existing tests' expectations. Touch existing production files only where the plan names a touch point; put new code in new files.
- Read `CONTRIBUTING.md` fully (updated today) and follow it in all new code: small cohesive types, explicit dependencies, interfaces defined at the consuming boundary (interface names end in `x` or are adjectives, e.g. `Remotex`; exported non-interface types are nouns; exported single-bool functions start with `Is`), functions named after the specific work they do (`Calculate…`, `Format…`, `Resolve…`; `Get` only for retrieving an existing value), boolean variables and predicates named as questions (`isHeld`, `areInputsUnchanged`), plural nouns for collections, `i/j/k` only for numeric counters (name iterated values by meaning), decisions in a focused function returning from each branch (no temp variable assigned per branch), guard clauses and early return with no `else` after a return, `continue`/`break` over nesting or stop flags, errors wrapped with `%w` plus operation and safe context, never ignore a cleanup error that could leave a lock or published state ambiguous, pass the caller's context, bounded detached context only for documented finalization, one owner per piece of mutable state, bounded concurrency, stop timers/child processes and close files on every exit path, no factories/wrappers/inheritance-like layers added just to name a pattern. Every exported declaration gets a doc comment that explains WHY it is shaped that way (match the register of the surrounding code). New files start with the SPDX header the neighbouring files use (`// SPDX-License-Identifier: GPL-3.0-or-later` + `// Copyright (c) 2026 yohimik`) when neighbours have it. No em dashes anywhere in comments, docs or messages; lowercase `dispat`.
- Code-style violations of CONTRIBUTING.md that you find in EXISTING code you touch: fix them carefully, purely mechanically, without changing behaviour or any test expectation, in a SEPARATE commit from feature work; keep exported names in pkg/* (add a documented deprecated alias if a rename is truly needed). No repo-wide sweeps. List them in your report.
- NEVER edit anything under specs/ccme-spec/. Another session owns the specification (decided by the repository owner). If an implementation fact contradicts the specification text, or a vector cannot be satisfied as written, do not change the text: state the fact in your final report under "Facts for the specification owner".
- Node identity in logs and events (gate 7b): every process of a distributed run logs through a logger that already carries `role` and `node` (the WRITER). Never add `Str("node", …)` yourself (it would duplicate the key in the JSON line); name ANOTHER node (the worker a task was placed on, the node a probe answered from) in the field `worker`. Webhook events are stamped with `role`/`node` by the dispatcher; set `worker` only on events of a stage that ran on a worker.
- Logging (zerolog, fields chained): trace = every operation, debug = decisions and diagnostic context, info = user-visible progress and outcomes, warn = recoverable conditions and every W diagnostic, error = failures; attach `code` for diagnostics; never log env values, command text, secrets or unredacted URLs (`gitx.RedactURL`). Main program events of the code you add must be covered at trace/debug, important user information at info.
- Performance and memory: no whole-file reads of build outputs (stream), bounded buffers, bounded goroutines, no leaked timers/goroutines/processes, avoid per-item git forks inside loops when one batched call exists.
- Tests: unit tests beside the code (services/dispat uses testify `assert`/`require` and `map[string]struct{…}` tables with `t.Run`; pkg/* uses stdlib `testing` only, message states the rule). Integration tests live in tests/integration, drive the compiled binary through `tests/integration/internal/harness`, author configs as typed `pkg/models` values (`harness.BaseFile`, `(*Repo).WriteConfigModel`; `WriteConfigRaw` only for shapes the model cannot express), assert on JSON events and git state, never on git/OS error wording, never `t.Skip` (the release gate runs the whole suite against a TinyGo binary and forbids skips; branch on `harness.IsTinyGo()` only for timing), use `harness.IsCodePresent`/`IsCodePresentForPackage`. The harness strips every `DISPAT_*` env var except `DISPAT_IT_*` and sets `DISPAT_UNSAFE_DISABLE_LOCK=true` by default (`harness.LockEnabled` re-enables the lock). EVERY new integration test needs a row in tests/integration/docs/test-plan.md (new `### Goal 57: distributed execution across worker nodes` section: if it does not exist yet, add the numbered prose goal under the right subject heading in `## Goals`, a line per new test file in the `## Architecture` tree, and the `### Goal 57` table `| Test | Claims proven |` in `## Coverage matrix`), and released behaviour claims get a row in tests/integration/docs/qa-requirements.md (6 cells, id like `EXE-12`, status `mapped`). `sh scripts/check-test-plan.sh` must pass.
