# Gate 12

## 1. Cancel / acknowledge
- Orchestrator: `Coordinator.cancel(attempt)` pushes X on the attempt's tip by CAS (tip may be A, C, H or G); a CAS loss re-reads once: if the tip is now R, take the result; otherwise follow the state machine. Triggers: run context cancelled (interrupt), a sibling decision that makes the task pointless is NOT a trigger (keep today's semantics: failures never abort independent work), authorize failure (gate 11), lock loss, `Close`.
- Worker: sees X on a branch it has claimed → cancels that task's context (the existing runner kills the process group; `WaitDelay` applies) → AFTER the process has exited pushes K (json: header + `phase` it was in: `inputs|before|commands|after|authorization-wait` + `commandStarted bool` for publish) → frees its slot. X on an unclaimed A: the worker never claims it (treat as closed). A worker shutting down (SIGINT/idle) cancels its tasks the same way and pushes R `cancelled` (or K when X was present) on a bounded detached context.
- Capacity: a node slot is returned ONLY on R or K. `timeouts.task` exceeded, or `timeouts.cancel` exceeded after X with no K → the slot is LEAKED for the rest of the run, the node is marked unhealthy (no further placement), warn `worker marked unhealthy` with node and reason enum. "A timeout alone cannot free capacity for a possibly overlapping attempt" (§28.2).
- Orchestrator interrupt (SIGINT on the release): cancel every in-flight attempt, await K up to `timeouts.cancel` on a detached bounded context, then proceed with the existing detached finalization (completeRelease's 5-minute budget, app/release.go ~:463) so already-published packages still get recorded; packages whose remote task was cancelled are `StatusCancelled` (not failed), exactly like a local interrupt.

- Queue time is not run time (review finding on gate 7's `Coordinator.awaitResult`, services/dispat/internal/execution/build.go): the task deadline currently starts when the orchestrator begins waiting, so an assignment that merely QUEUES in the mailbox behind another run's task on a shared worker (spec vector 21) can time out without ever having started, which leaks the slot and marks a healthy node unhealthy. Split the wait in two phases using what the watcher already observes: (a) UNCLAIMED (tip is still A): bounded by `timeouts.task`; on expiry WITHDRAW the assignment with a compare-and-swap delete of the ref against A's object id: if the delete succeeds the task provably never ran, so the slot is returned (not leaked), the node stays healthy, and the task is placed again (on any compatible node, this one included) under a NEW attempt number and a new branch; if the delete loses the race because the worker claimed meanwhile, continue in phase (b); bound re-placement to a small number of attempts (3) so a permanently full pool fails the task instead of looping, with a message that says the pool had no capacity. (b) CLAIMED (C observed): the `timeouts.task` clock starts at the claim; expiry is the leaked-slot, unhealthy-node path described above. Unit-test the two phases with a fake transport and clock; integration: extend `TestExecutionWorkerCapacityHoldsAcrossRuns` (or add `TestExecutionQueuedWorkIsNotATimeout`) with a short `timeouts.task` that is longer than one build but shorter than two queued builds: both runs still complete and no node is marked unhealthy.

## 1b. Deadlines the worker enforces itself, and a bounded authorization (spec-audit findings 3 and 4, adopted)
- Every assignment carries `deadlineSeconds` (the orchestrator's `timeouts.task`). The WORKER enforces it on its own clock from the moment it claims: at the deadline it cancels the task context (the existing runner kills the process group), and reports `failed` with `failedPart: "deadline"`. An orchestrator that died or lost its network therefore cannot leave a task running forever on a worker.
- The publication authorization G (gate 11) carries `notAfter` (RFC3339, = issue time + a small window such as 120 s). A worker that observes G after `notAfter` MUST NOT start the publish command (it answers `failed`/`authorization-expired`). Together these give a STATED bound the docs can rely on: a publisher authorized by G has stopped by `notAfter + deadlineSeconds`, assuming clocks within the 24 h replay window's skew tolerance are actually close; say so as an assumption, never as a guarantee of automatic lock takeover: a retained lock is still cleared by an operator.
- The E228 error line and the retained-lock error name the RUN ID and tell the operator, in this order: (1) list the mailbox refs of that run (`dispat-worker-*`), (2) look for an authorization without a result (G with no R) and confirm on the worker that the publisher stopped (or wait past the stated bound), (3) check the registry for the version, (4) delete the run's refs, (5) only then delete the lock tag. If it is cheap, put the run id into the lock tag's message for distributed runs only (look at `lockMessage`, services/dispat/internal/release/lock.go ~:301; the run id would have to be minted before lock acquisition: do it only if it needs no restructuring, otherwise log the run id beside the lock acquisition line and say so).

## 2. Lock loss
- Besides the pre-authorization check (gate 11), the Coordinator re-verifies lock ownership before EVERY new assignment (one `ls-remote` per owning repository, cached for at most 5 s so a fan-out does not multiply it). Lost → no new assignment and no new authorization is issued ("After lock loss, no new effect may start"): in-flight compute attempts are cancelled; an in-flight AUTHORIZED publisher is left to finish or be reconciled per §3 below, and a publication that was authorized BEFORE the loss and reports success is still RECORDED (tag, changelog, release commit): recording is not a new effect, it is the create-only record of an effect that already happened, and skipping it would leave a published, unrecorded package for the next owner (spec-audit finding 2); the run fails with E336, category `native-recording-or-lock`. The lock that was lost is NOT deleted or re-created by this run (never delete another run's lock; CONTRIBUTING "Release safety").

## 3. Publication outcome unknown (E228, category `publication-unknown`): extend the single function gate 11 left for this
An attempt is "authorized" from the moment the Coordinator decided to push G (mark before the push; a G push whose response was lost and whose tip re-read is ambiguous counts as authorized).
- Authorized + R arrives (any status): known outcome. `succeeded` → normal `publishTail`. `failed` → package failed at publish (the publisher reported its own failure; same semantics as a local failed publish command).  `cancelled` with `commandStarted=false` → known not published → StatusCancelled/failed per trigger. `cancelled` with `commandStarted=true` → the command was killed mid-way: outcome UNKNOWN for the package (E228) but the publisher is QUIESCED.
- Authorized + no R within `timeouts.task`: push X, await K up to `timeouts.cancel`. K with `commandStarted=false` → known not published. K with `commandStarted=true` → unknown outcome, quiesced. No K → unknown outcome, NOT quiesced.
- For every unknown outcome: the package's result is failed at stage `publish` with E228, NO tag/record is written (neither a missing reply nor a missing tag proves failure: nothing is inferred either way), NO second attempt is authorized in this run (single-use authorization; "never infer a failed publish from the timeout"), dependents are blocked by the ordinary rules, unrelated safe work continues, the run is reported INCOMPLETE and exits non-zero, the summary lists the package under unknown external outcomes with run/task/attempt/node/repository identities.
- Lock handover: if every unknown attempt is quiesced (K received) → locks are released normally at the end. If ANY authorized attempt is not quiesced → the OWNING repository's lock (and only that one; other repositories' locks are released in reverse order as usual) is RETAINED: `unlock` skips it, logs `Error()` with code E228, category, the lock tag name, the redacted remote and a remedy naming the release-lock documentation page ("clearing a lock that was left behind": packages/docs/docs/reference/releasing/release-lock.md) and states that the operator must confirm the publisher stopped and reconcile the registry before clearing it. Never report successful cleanup in that case; exit non-zero. Implement by letting the unlock path ask the Coordinator which repositories must stay locked (a small interface at the consumer: app/release.go single-history unlock closure and `workspaceRecorder.unlock`, app/polyrepo_record.go ~:110); behaviour without a Coordinator is unchanged.
- dispat has no registry identity check (§19.4 is delegated to the publish command; see packages/docs/docs/internals/architecture.md "Deliberately out of scope"): the NEXT run's ordinary publish is the repeatable publisher, exactly as after an interrupted local publish today. Do not invent a reconciliation command in this gate.
