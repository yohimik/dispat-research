## Facts added after gate 12-13 merged (2026-09-22)
- Cancellation and capacity (execution/cancel.go, withdraw.go): a slot returns only on a result, an acknowledged withdrawal (K carries `phase` and `commandStarted`), or a revoked coordination ref of an assignment nobody claimed. A task deadline has two phases: the queue (unclaimed: the assignment is revoked by CAS delete and the task is placed again, up to 3 placements) and the run (claimed: the clock starts at the claim). A timed-out claimed attempt leaks its slot and takes the node out of the pool (`unhealthy`, reasons `task-deadline`, `cancel-unacknowledged`, `transport`). Every assignment carries `deadlineSeconds`, enforced by the node itself.
- Lock loss (execution/ownership.go, app/execution_locks.go): ownership is re-verified against the remote before every new assignment and authorization (5 s cache); a loss halts every attempt in flight (withdrawn like an interrupt) and the run ends with E336; recording a publication authorized before the loss still happens. Document that one failed read of the lock is currently treated as a loss.
- Outcome unknown (execution/unknown.go): a publication authorized (G written) with no result: the run withdraws it and waits `timeouts.cancel`; an acknowledgement saying the publish command had not started = ordinary publish failure; an acknowledgement after the command started, or no acknowledgement = E228 `publication-unknown`, no second attempt in this run; the owning repository's release lock is RETAINED only when the publisher never acknowledged (`quiesced=false`), and the error names the order of recovery (list the run's `dispat-worker-*` refs, find the authorization with no result beside it, confirm on the node that the publisher stopped, check the registry, delete the run's refs, then delete the lock tag). A run may end with its lock retained and NO record.
- Summary (execution/summary.go, app/execution_summary.go): one line per task in plan order with placement (`here` for the orchestrator's own slot, prepared providers, blocked rows), computation / outputs / publication / recording apart, totals, and an `execution metrics` line (queue and run time per task, bytes, files, git invocations, cold/warm cache). No speed-up claim anywhere.
- Worker: `--idle-timeout` counts from the last activity (a task in flight never counts as idle); transport branches (snapshot, relay) are skipped at trace level; a withdrawal is verified (signature, header, chain) before the work is stopped; a node re-reads its branch after a refused push.
- Docker/TinyGo gate: the integration suite is about 26 minutes natively and longer under the tiny binary; the Dockerfile's `-timeout` is being raised by gate 16 (say nothing about it in user docs).
- Placement bugs seen in the field (Linux farm, LLVM): a heterogeneous pool makes a release wait for its slowest node because placement is first-free; the documented remedy is homogeneous workers or two classes through `runOnly`; a speed hint is a listed follow-up.
- Snapshot cost: the first push of a repository's prepared state to a mailbox that shares no objects with it carries the whole history (7.3 M objects / 3.6 GB for LLVM, 17 minutes); cleanup deletes every ref so the cost repeats per run unless the mailbox is the run's own origin or keeps objects. Document under "what to watch for" with the remedy (mailbox = a clone of the origin, or the same bare repository).
- A result carrying build outputs reports under `transfer.timeout`; a result carrying nothing under a fixed 30 s bound.
