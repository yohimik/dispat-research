## The corrections (each is a small, surgical edit inside §28 unless noted)
1. §28.4 branch naming. Replace the `worker-<date>-<random>` rule with: coordination branches are named `dispat-worker-<id>-<workinfo>`, created atomically under `refs/heads/`. `<id>` is the node name of the execution link the branch is addressed to. `<workinfo>` is `<date>-<kind>-<random>`: the date SHOULD be UTC `YYYYMMDD` and is a diagnostic label only; `<kind>` is a short lowercase label of the work (for example `probe`, `build`, `publish`, `prepare`, `snapshot`, `relay`) and is also diagnostic only; the random suffix MUST provide at least 128 bits of cryptographic randomness. The name is an untrusted routing hint that lets a node list only the branches addressed to it; the authenticated manifest, not the branch name, identifies node, run, task and attempt, and a node MUST reject a manifest whose node or branch binding disagrees with where it was found. Keep: a branch is bound to one run, repository and task attempt; parallel attempts never share a mutable branch. Update every other occurrence of the old name in SPEC.md, README.md (and nowhere else; check `grep -rn 'worker-<date>' specs packages/docs/docs`).
2. §28.4: both the orchestrator and the assigned worker MAY advance an attempt's branch, each update checking the expected previous object ID and attempt ownership (the text today only says ref updates check the expected previous object ID; make the two-writer model explicit).
3. §28.4 "Each acknowledged checkpoint MUST identify an exact full object ID; consumers fetch that object…": add that a consumer MAY obtain the object by fetching a ref that advertises it and then resolving the exact object ID locally, and MUST read only from that object ID, never from a moving tip.
4. §28.6 publication authorization: state that authorization is an explicit, single-use step bound to the task attempt, issued by the orchestrator only after the package's pre-publication hook has completed on the executing node and after the relevant-input and lock-ownership checks, and that the publisher MUST NOT start its publication command before it has observed that authorization (this preserves §27.2's "immediately after beforePublish and before the publish command" revalidation when the hook runs on a worker).
5. §28.6 fencing of compute-only attempts: an attempt that was never authorized to perform an external effect (no publication authorization, no native-ref permission) is safely fenced by revoking its transport ref so its expected-old-ID update can no longer succeed; releasing repository locks need not wait for that attempt's acknowledgement. An authorized publisher still requires acknowledged cancellation, effective fencing or reconciliation exactly as the section already says.
6. §28.3 assignment contents, "Secret references are separate from logged or transported public metadata": add that a command environment derived from secret references travels as references and is resolved on the executing node from that node's own environment; resolved secret values MUST NOT be written to transport branches, manifests, receipts or logs.
7. §28.3/§28.6 "ownership generation": define it for the Git release-lock convention as a value derived from the identities of the lock objects this run holds (for example the lock tag object IDs of every participating repository), so a new acquisition always yields a new generation.
8. §28.9: give each of the six categories a stable machine identifier, stated in the table (add a column or a parenthetical): `execution-configuration`, `execution-authority`, `io-integrity`, `publication-unknown`, `native-recording-or-lock`, `transport-cleanup`. Keep the sentence that these are not allocations of new `E`/`W` numbers; implementations MAY additionally attach their own numbered codes.
9. §28.8 vectors: make 13 and the publisher half of 14 explicitly apply "where publication commands execute on workers"; make the second sentence of 22 conditional ("where the implementation admits execution-only edges that the release graph does not already reject"); make 26 conditional on the implementation advertising §26 rollback; make the reuse sentence of 20 conditional ("where verified outputs are reused across runs"). A vector whose condition does not hold for an implementation is not applicable to it; say so once in the introductory line of §28.8 rather than in every vector.
10. §28.1 "Every node MUST support both roles": clarify that one engine provides both roles and that serving delegated tasks MAY be a distinct invocation or process of that same engine (for example a long-running serving command), without a separate worker product or configuration format.
11. §28.3 shared manifest/lockfile reconciliation ("one explicit preparation task per affected input state, performed once before the affected builds fan out…"): restate so it is implementable by an engine whose preparation is per package: every reconciliation that writes a shared manifest or lockfile is an explicit task executed under the orchestrator's authority, never implicitly by workers; such tasks serialize per shared file; each build binds, in its manifest, the exact admitted prepared input state it consumed; builds fan out only from an admitted state, and a later shared mutation creates a new state rather than mutating one a running build consumes. Keep the existing prohibitions (workers MUST NOT each regenerate and race to merge a workspace-wide lockfile; a later required shared mutation invalidates affected outputs; do not force all builds onto one node). Update vector 18 wording to match (preparation executes under the orchestrator only, serialized, and each build records the admitted state it consumed; consumers of one state see identical bytes).
12. Hook placement (new short paragraph in §28.6 or §28.3, wherever it reads naturally): hooks bracketing a delegated stage execute with that stage on the executing node under worker authority; run-level hooks, recording, observational post-publication hooks, failure hooks and folder reverts execute under the orchestrator.
