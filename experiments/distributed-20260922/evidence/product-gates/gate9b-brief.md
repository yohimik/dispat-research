## Why
A worker executes commands on another machine. Some work must never leave the machine that holds the credentials or the trust: signing, a publish that logs in, a build whose artifact is too sensitive to take from a worker. The operator needs to say so in configuration, per package and per stage.

Shape: mirror `concurrency`, which the language already writes as "one value for both stages, or a `[build, publish]` pair" (pkg/models `Concurrency`, its decoder `nums` in services/dispat/internal/config/fields.go, `validateConcurrency`): `runOnly: orchestrator` applies to both delegable stages; `runOnly: [worker, orchestrator]` says build on workers, publish on the orchestrator. `build` and `publish` are the only stages a run ever delegates; version, syncLock, login, recording and every run-level hook always run on the orchestrator and are not configurable. ## The placement decision (one focused function, returning from each branch)
A stage's FRAME is its before hook, its stage commands and its after hook (build: `beforeBuild`, `build`, `postBuild`; publish: `beforePublish`, `publish`). A frame always runs as ONE unit on ONE node. `runOnly` is a placement filter exactly as `buildPlatforms` is one:
- `orchestrator`: the frame runs on the orchestrator.
- `worker`: the frame runs on a worker. A release whose plan contains such a stage while the entry configuration has no worker links cannot run it: refuse the release before any stage runs (E225, naming the package, the stage and the missing `execution.workers`); `dispat status` still works and says nothing (it executes nothing).
- `both`: any node. The orchestrator takes part in placement as one more node whose capacity is its own `execution.concurrency` (spec §28.1: the orchestrator "MAY execute tasks locally under the same rules"), preferred LAST: it is chosen only when no compatible worker has a free slot, so that it stays free for the version, syncLock, publish and recording work only it can do. Implement it in `Pool` as a node flagged local (not as a fake mailbox): `Acquire(ctx, platforms, runOnly)` filters by platform AND by the flag; the lease says whether the placement is local.
- `publish` of a package whose space has a login script: the orchestrator, whatever `runOnly` says (`worker` there was already refused at load). Gate 11 implements remote publish and must call this same decision.
With no `execution` object, or no worker links and no `worker` value in play, the key is validated and otherwise inert: every stage runs locally as it always did, byte for byte.

## Running a build on the orchestrator inside a distributed run ("the orchestrator is also a node")
Spec §28.1: the orchestrator "MAY execute tasks locally under the same rules". In `runStage` (services/dispat/internal/release/remote.go), a `taskBuild` placed on the orchestrator (pinned by `runOnly: orchestrator`, or chosen by the pool under `both`) takes the local path (`stageFrame`, bracketed by the same `Guard` slot accounting gate 7 gave version/syncLock so the node's `execution.concurrency` still bounds it), and then its results must be as usable by other nodes as a worker's:
- BEFORE the frame: every provider output the build needs is already installed in the orchestrator's checkout for RELEASING providers (gate 9 installs admitted outputs locally). For non-releasing providers gate 10 (`ensurePrepared`) will cover it; if gate 10 is not committed yet, make the local path call the same "make sure my providers' outputs are present here" routine the remote path uses, or leave a single clearly named function for gate 10 to fill and say so in your report.
- AFTER a successful frame: capture the package's declared `buildOutputs` FROM THE ORCHESTRATOR'S CHECKOUT with the same capture routine a worker uses (same refusals: absent root, gitlink, limits, case-fold collision), build the same manifest (node = the orchestrator's name, platform = this machine's), create the result commit in the local object store and ADMIT it through the same admission code path a worker's result goes through (so consumers receive `{branch, commit, manifestDigest}` inputs of identical shape); offer it to a consumer's endpoint lazily, as an immutable create-only `…-relay-…` branch, when a consumer placed on that endpoint needs it (gate 9's relay routine). Nothing is installed locally (the bytes are already there).
- A failure of the local frame fails the package exactly as a local failure does today (`onFail`, revert, labels unchanged).
- The summary/task records (gate 13 will print them) mark the task's node as the orchestrator.
A pinned PUBLISH is simply the local path; gate 11 owns wiring the decision into publish. If gate 11 is already committed when you run, wire it there now and test it; if not, leave the boolean computed and tested at the config level and say so.
