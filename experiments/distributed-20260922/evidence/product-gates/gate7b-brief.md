## The rule to implement
Every process that takes part in distributed execution says who it is on EVERY log line it writes and in EVERY webhook event it sends, with two fields:
- `role`: `orchestrator` or `worker`;
- `node`: the node's name. A worker's is its `execution.name`. An orchestrator's is its `execution.name` when stated, otherwise the machine's host name (`os.Hostname()`, falling back to the literal `orchestrator` when that fails).
`node` therefore ALWAYS means "the node that wrote this line / sent this event". A line or event that is ABOUT another node (the orchestrator reporting which worker a task was placed on, which worker answered a probe, which worker became unhealthy, which worker ran a stage) names that other node in a separate field `worker`. Gate 6 and 7 orchestrator-side log lines currently use `node` for the worker they are about: rename that field to `worker` on the orchestrator side (worker-side lines keep `node`, where it already means the writer). Update the unit and integration tests of gates 6-7 that read those fields (they are this feature's own tests; existing tests of other features must not change).
When the entry configuration states no `execution` object at all, NOTHING changes: no `role`, no `node`, no `worker` field anywhere, log lines and webhook payloads byte-for-byte what they were (spec vector 1; the integration suite's existing expectations must pass unmodified). The fields appear exactly when `cfg.Execution != nil` for a release-side command, and always for `dispat worker`.
